Phase 1Grounding Context

The product (greenfield)

Tablemarks saves restaurants — favorites and to-try — on a map. Per place: address, category (burger / French / Indian…), visit date, rating, Google Maps link. It must work two ways: signed in with Google (cloud sync via PocketBase) or local-only with no account (localStorage). Single-user personal tool — simple and modern, not a social MVP. Free: no design that leans on paid Google Maps API quota.

What external research established (2026)

  • Maps: Leaflet + react-leaflet v5 is the pragmatic default — no API key (OSM tiles), no WebGL dependency, React 19 + TS support, custom DivIcon category markers, clustering via react-leaflet-cluster. MapLibre only if custom basemap styling is wanted.
  • Geocoding (no paid quota): Nominatim / Photon (no key, ~1 req/s, typo-tolerant) or Geoapify (3k/day free key). A pasted Google Maps URL yields coords via the /@lat,lng/ segment; shortened maps.app.goo.gl links need a server-side redirect resolve — the browser can't follow it cross-origin.
  • PocketBase v0.39: one-line Google OAuth2; no built-in offline queue or CRDT. Community pattern: write localStorage always, push when online, mark a synced flag, subscribe('*') for multi-device, last-write-wins on updated. "Start local → sign in → migrate" is a DIY batch-create.
  • Stack: React 19 (useOptimistic for instant marker add), Vite 7 (Node ≥20.19, ESM-only), Tailwind v4 (config-less, @import "tailwindcss"). Client-only SPA — no Server Components.
  • Offline: vite-plugin-pwa makes it installable; a Workbox CacheFirst rule on OSM tiles (~500 cap) progressively caches seen areas. Full-city tile download (hundreds of MB) is not worth it.
  • Prior art: Mapstr (map-first, tags, no rating, read-only offline), Beli (explicit been / want-to-try dual list, cuisine filter), Google Maps Saved (star affordance, named lists, but locked-in / no export). Patterns to adopt: map-first + bottom sheet, category-colored markers, status badge + filter, add-via-search OR paste-URL, PWA.

Top pick — R1. R1 Paste-a-URL capture, zero typing Capture & data model

Description
Make a pasted Google Maps link the primary — often the only — input. Parse coordinates client-side with /@(-?\d+\.\d+),(-?\d+\.\d+)/ and pull the place name from the /maps/place/Name/ path segment. For the mobile maps.app.goo.gl short links (Google's default share format), a small PocketBase Go hook follows the redirect server-side and returns coordinates. The marker drops instantly via useOptimistic; category, rating, and date are deferred-optional — fill them later, or never.
Basis
direct Grounding documents the coordinate regex, the place-name path segment, and that shortened links "need a server-side redirect resolve (PocketBase hook) — browser can't follow cross-origin redirect"; useOptimistic is named for instant marker-add.
Rationale
The dominant capture moment is sharing a place from Google Maps. If saving it demands a 5-field form, the save never happens. One paste → a pin in under 3 seconds keeps the collection alive.
Downsides
Short-link resolution is server-side, so it isn't pure-client — and an offline short-link add can't resolve coords until reconnect (queue it). Google can change its URL format, which would break parsing.
Confidence 90% Complexity Medium

R2 Local-first canonical architecture Auth & sync

Description
localStorage is always the master copy, even when signed in; PocketBase is a mirror, not the source of truth. There is no "local mode vs cloud mode" toggle to choose — everyone starts local with no account, and signing in is framed purely as "back up + sync across devices," which triggers a one-time batch-create migration of existing local records. The two required modes collapse into a single code path with one substrate.
Basis
direct Grounding prescribes "write to localStorage always; push to PocketBase when online" and "Start local → sign in → migrate is DIY: batch-create local records." external Obsidian's local-canonical model (sync is a feature you turn on, not a precondition).
Rationale
Removes an onboarding decision entirely, guarantees the app fully works offline / account-free, and means there's never a scary one-way "switch to cloud" door. It's also the cheapest way to satisfy the hard both-modes constraint — one path instead of two.
Downsides
The ~5 MB localStorage ceiling becomes load-bearing — a user who crosses into hundreds of entries (especially with photos) needs an escape valve to IndexedDB. The mirror-vs-master invariant has to be enforced carefully so a stale cloud read never clobbers fresh local data.
Confidence 88% Complexity Medium

R3 Visits as a log + returnability verdict Capture & data model

Description
Model a restaurant as a parent with many timestamped visit children (PocketBase one-to-many), not a flat record with a single visit_date. "To-try" becomes "zero visits"; "visited" is "≥ 1 visit" — the status field disappears as derived state. Replace the 1–5 star number with a returnability verdict per visit — Go back / Worth a detour / Once was enough / Never again — and show the latest verdict plus a visit count on the card. A one-tap "I'm here now" appends a visit.
Basis
external Last.fm scrobbling (append-only events make the history the asset) and Beli's been/to-try framing. reasoned For a personal "where do I eat" tool the actionable question is "would I return?" — a verdict answers it directly; a number obscures it. direct Grounding lists visit-date and rating as flat fields, so this is a deliberate inversion of the given model.
Rationale
The single highest-compounding schema choice. Over two years, a log of dated visits with verdicts is a personal dining memory ("been to Chez Marcel 4× → clearly a Go-back"); a flat overwritten date is just a list. Decided now it's free; retrofitted later it's a migration.
Downsides
More schema up front, and the rollup rule (show latest verdict? most frequent?) needs a call. Verdict-instead-of-stars is opinionated — some users want a number. The append-only history must stay cheap to write or the one-tap promise breaks.
Confidence 75% Complexity Medium

R4 "Where do I eat tonight?" decision engine Map & discovery

Description
A dedicated mode that turns the saved set into a decision, not just a catalog. The free Geolocation API + Leaflet map.locate() center on the user, filter to to-try places within a radius (0.5 / 1 / 5 km), combine with cuisine and verdict filters, then surface a short shortlist or a "spin the wheel" pick. It answers "what nearby did I actually want to try?" in one tap.
Basis
reasoned The unspoken job of a to-try list is eventual decision, yet the prior-art apps (Mapstr, Beli, Google Saved) catalog without closing the decision loop. direct Geolocation API is free and built-in, map.locate() is documented Leaflet, and the radius filter is pure client-side logic — no quota touched.
Rationale
Shifts the success metric from "saved places" to "picked a place." A map of 80 pins is a worse decision tool than three candidates near you right now — this is the feature that earns a Friday-night open.
Downsides
The geolocation permission prompt is friction. "Open now" would need opening-hours data, which the free stack doesn't carry — so the mode is "want to try nearby," not "open near me." Radius defaults need tuning per user (urban vs rural).
Confidence 85% Complexity Low–Medium

R5 Faceted classification & filtering Categorization & organization

Description
Instead of one fixed "category," each place carries orthogonal facets — cuisine, status/verdict, and occasion (date-night / quick-lunch / group). The map and list filter by any combination ("Indian + to-try + near work"). A single CATEGORY_COLORS constant drives both the Leaflet DivIcon marker color and the filter chips, and non-matching markers dim rather than disappear, so spatial context is never lost.
Basis
reasoned Single-category taxonomies force false choices — a place is Indian and date-night and to-try at once; library-science faceted classification solved exactly this "one item, many access paths" problem. external Grounding's "cuisine filter sidebar expected" lesson from Beli.
Rationale
Faceting is what keeps a growing collection queryable instead of a flat pile. The single-source color contract stops the map and the filter UI from drifting apart as the category list grows from 5 to 20.
Downsides
More filter UI to design and a real risk of over-faceting for a personal tool — it needs sensible defaults and a way to stay out of the way. The "occasion" facet is speculative until the user actually wants it; ship cuisine + status first.
Confidence 70% Complexity Medium

R6 Own-your-data: export/import + PWA offline Offline & portability

Description
Two halves of data ownership. (a) One-click export to JSON/GeoJSON with a stable, documented schema; import upserts by stable ID so round-trips are safe — a direct answer to the Google-Maps lock-in the research flags. (b) vite-plugin-pwa makes the app installable and viewable offline; a Workbox CacheFirst rule on OSM tiles (~500 cap) progressively caches the areas you've seen, with an optional one-time neighborhood prefetch on install so the first offline open isn't a blank grey map.
Basis
direct Grounding names export as a differentiator ("Google Maps Saved is locked-in / no export"), recommends vite-plugin-pwa, specifies the Workbox CacheFirst tile rule with a ~500 cap, and rules full-city tile download out as "not worth it."
Rationale
For a personal tool, knowing you can leave with your data — and that it works on a plane or a subway platform — is a precondition for trusting it long enough to build a multi-year collection. Offline is also an explicit feature in the spec, not a nice-to-have.
Downsides
Service-worker update/staleness is a classic PWA footgun; globPatterns:['**/*'] is required or images silently miss the cache. The export schema becomes a compatibility contract you have to version as the model evolves.
Confidence 85% Complexity Medium

R7 Sync trust layer Auth & sync

Description
Make sync state legible rather than invisible. Each record carries a synced: boolean; a persistent "N unsynced" badge shows pending writes; offline writes queue and auto-flush on the next online event. For multi-device last-write-wins, surface the discard instead of silently overwriting — a git-merge-style ribbon: "kept the newer rating, discarded the older one · undo."
Basis
direct Grounding's sync pattern uses the synced flag and accepts last-write-wins on updated. external Git made merge conflicts a visible, recoverable event rather than a silent overwrite — the structurally identical failure mode here.
Rationale
R2 makes sync exist; this makes it trustworthy. Without a visible queue and conflict surfacing, a spotty-connection save that looks saved but isn't — or an edit silently dropped on another device — teaches the user to distrust sync and retreat to local-only, defeating the whole feature.
Downsides
For a single user the multi-device conflict rate is near zero, so the conflict ribbon risks being over-engineering — keep it minimal. The offline queue needs to persist correctly across reloads, which is the part that actually bites.
Confidence 72% Complexity Medium
